
# Plan Detallado de Resolución para Briki

## 1. Asociación de Clientes en el Formulario del Chat

### Objetivo
Lograr que, al llenar el campo “Cliente” en el formulario del panel derecho del chat, el usuario pueda seleccionar entre sus clientes existentes mediante un desplegable/autocompletado. Si el nombre ingresado no existe, se debe ofrecer la opción de crear el cliente y asociarlo al usuario, mostrando una advertencia y permitiendo la creación rápida.

### Implementación

#### a) Consulta y Desplegado de Clientes Existentes
- Al renderizar el formulario, realizar una consulta al backend para obtener la lista de clientes asociados al usuario/organización actual.
- Mostrar estos clientes en un componente de autocompletado/desplegable en el campo “Cliente”.
- El autocompletado debe permitir seleccionar un cliente existente o escribir uno nuevo.

#### b) Validación de Cliente al Enviar el Formulario
- Al intentar enviar el formulario, verificar si el nombre ingresado corresponde a un cliente existente.
- Si el cliente existe, asociar el caso al cliente seleccionado.
- Si el cliente NO existe, mostrar un modal con el mensaje:  
  “El cliente 'Cliente' no existe entre tus clientes registrados, ¿Deseas crear a este nuevo cliente? (Deberás completar sus datos en tu gestor de clientes después)”
- Si el usuario acepta, crear el cliente en la base de datos con solo el nombre y asociarlo al usuario/organización actual.

#### c) Unificación de Lógica en los Tres Botones
- Los tres botones (“Aprobar” debajo del mensaje, “Guardar caso” en el formulario, “Aprobar y seguir con análisis” en el panel de respuestas) deben ejecutar la misma lógica de validación y creación de cliente.
- Centralizar la función de validación/creación para que todos los botones la utilicen.
- Tras guardar el caso y asociar el cliente, avanzar a la siguiente etapa del flujo (simulación de análisis del agente).

#### d) Persistencia y Seguridad
- Al crear un cliente, guardar únicamente el nombre cifrado en la base de datos (cumpliendo con la arquitectura actual de cifrado PII).
- El cliente debe quedar asociado a la organización/usuario actual.
- El caso debe guardar la referencia al cliente (por ID).

#### e) Actualización de Estado Global
- Usar el estado global (Zustand) para mantener la referencia al cliente y caso activo durante el flujo.

## 2. Solución al Error ChunkLoadError en Páginas Dinámicas

### Objetivo
Eliminar el error `Runtime ChunkLoadError` que ocurre al cargar por primera vez las páginas `/workspace/clients/new` y `/workspace/cases/[id]`, evitando la necesidad de refrescar la página.

### Implementación

#### a) Diagnóstico del Problema
- El error ocurre porque Next.js no encuentra el chunk JS correspondiente a la ruta dinámica, generalmente por problemas de despliegue, configuración de rutas, o incompatibilidad con el sistema de locales.
- Puede estar relacionado con la forma en que Next.js genera y sirve los archivos estáticos para rutas dinámicas y localizadas.

#### b) Acciones Técnicas
- Verificar que el despliegue (por ejemplo, en Vercel) esté sirviendo correctamente los archivos estáticos y chunks generados por Next.js.
- Revisar la configuración de rutas en `next.config.ts`, asegurando que las rutas dinámicas y los locales estén correctamente definidos.
- Confirmar que no hay problemas de caché o CDN que impidan la carga de los chunks.
- Validar que los imports y exports en los archivos de las páginas dinámicas sean correctos y no generen dependencias circulares o incompatibles con SSR/Edge Runtime.
- Si se usan middlewares, asegurarse de que sean compatibles con Edge Runtime y no dependan de módulos Node.js no soportados.

#### c) Mejoras de Robustez
- Implementar un fallback de error en el frontend para mostrar un mensaje amigable si ocurre un ChunkLoadError, permitiendo al usuario reintentar la carga sin perder el contexto.
- Documentar el proceso de despliegue y los requisitos para servir correctamente los chunks estáticos.

## 3. Esquema de Base de Datos y Seguridad

### Estructura Relevante
- **Clientes**: Tabla `clients` con campos cifrados (nombre, email, teléfono, dirección), asociados a la organización.
- **Casos**: Tabla `cases` con referencia al cliente (`clientRef`), organización (`orgId`), y datos del caso.
- **Usuarios y Organizaciones**: Tablas `users`, `org_members`, `organizations` para multi-tenancy y seguridad.
- **Auditoría**: Tabla `audit_log` para registrar todas las acciones importantes.

### Seguridad
- Todas las operaciones deben respetar la seguridad por organización (RLS).
- Los datos personales de clientes deben estar cifrados en la base de datos.
- El sistema de autenticación está unificado bajo Supabase Auth.

## 4. Resumen de Flujo para el Desarrollador

1. Al abrir el formulario del chat, cargar y mostrar los clientes existentes en un autocompletado.
2. Al enviar el formulario, validar si el cliente existe; si no, ofrecer crearlo y asociarlo.
3. Centralizar la lógica de validación/creación para los tres botones de acción.
4. Guardar el caso con la referencia al cliente y avanzar en el flujo.
5. Solucionar el error de carga de chunks revisando configuración, despliegue y robusteciendo el frontend.
6. Mantener la seguridad y cifrado de datos en todas las operaciones.
